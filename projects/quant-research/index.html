ENGINEERING CASE STUDY

Data validation & mutation testing

Replacing a misleading pass count with real execution and tests that detect injected defects.

01

Engineering problem

An earlier stress runner reported 5,000 passes without calling the validators it was meant to exercise. The number looked reassuring but could not establish that the relevant safeguards worked.

02

Design decision

Replace pass-count evidence with tests that exercise the public API and CLI. Then challenge those tests by deliberately weakening safeguards and checking whether the suite detects the change.

03

Implementation

The repaired suite runs the actual validation path, including real-file cases. Mutation checks introduce specific defects into the protection logic and require the corresponding tests to fail. A passing baseline is checked before the mutations are evaluated.

The condition the system must preserve

A test result must exercise the actual validation path and fail when a targeted safeguard is deliberately broken.

How the implementation works

  1. 01

    Trace what the old runner executed

    Review the runner behind the 5,000-pass report. It did not call the validators it claimed to exercise, so its counter could rise without testing the relevant behavior.

  2. 02

    Exercise the public API and CLI

    Run the real validation entry points, including cases that read actual files. This ties the result to executable input handling rather than a success counter detached from the implementation.

  3. 03

    Establish a passing baseline

    Run the repaired suite against the unchanged implementation before injecting defects. A baseline failure cannot be counted as evidence that a mutation was detected.

  4. 04

    Challenge the safeguards

    Introduce nine defined mutations into protection logic and check that the corresponding tests fail. Record both the baseline and mutation outcomes so the checks can be distinguished.

04

Design considerations

Narrowing the executable scope makes verification more concrete, while leaving larger research and trading features outside the current result. A useful test count needs a clearly defined behavior behind it.

05

Verification

Archived Linux verification records show 79 tests passed without skips, including two real-file tests. All nine injected mutations were detected. These are recorded software verification results.

Implementation and test references

References are from the archived v10.66 research repair. The execution results belong to its recorded Linux environment.

mutation_check.py
First checks that each target test passes on the normal implementation. Injects one safeguard defect at a time in a temporary copy and does not count an unrelated process error as detection.
tests/test_pipeline.py
Executes the actual Python API and subprocess CLI, checking repeat-run idempotency, recomputed results, and rejection of tampered output.
tests/test_real.py
Uses an externally supplied fixture package for two real-file cases. Verifies hashes, parsing, and reruns while explicitly rejecting a claim of backtest readiness.

The recorded run included both real-file cases and detected all nine defined mutations. Running these cases again requires the corresponding external fixture package.

06

Implementation status

Mac verification remained unfinished at the reviewed checkpoint. The project has not established a working trading strategy, live trading, or historical backtest readiness.
