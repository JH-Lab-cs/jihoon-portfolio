01 / Overview

Placia

Placia is a private, on-device travel photo atlas. The product organizes travel memories around photos and places. This case examines the internal backend for creating an identity, approving a first device, and issuing a session.

02 / The problem

The problem

Two accounts could compete to register the same device keys. An interrupted first login could also consume authorization without leaving a usable account and session. The important failure was a partially completed state that looked valid to the next request.

03 / The decision

The decision

Treat first login as one state transition. Identity creation, first-device approval, session issuance, and an encrypted retry response are committed together in a PostgreSQL transaction.

04 / How it works

How it works

Device and key reservations acquire locks in a fixed order. Deferred database constraints reject incomplete transactions. An identical retry returns the existing session, so retrying does not create a second independent login result. Regression cases also cover cleanup during authorization expiry.

05 / The tradeoff

The tradeoff

The stronger consistency boundary adds locking, database constraints, and encryption-key management. Those mechanisms become part of the behavior that integration tests need to exercise.

06 / What was verified

What was verified

The recorded implementation checkpoint passed 201 unit and HTTP tests and 70 PostgreSQL integration tests, alongside type checking, lint, build, and CI. The regression set includes concurrent key registration, incomplete transactions, and expiry cleanup.

07 / Current scope

Current scope

This is an internal authentication-service case study. At the reviewed checkpoint, public authentication routes were not enabled in the executable. A released connected-login experience is outside this result.

ABOUT THE EVIDENCE
